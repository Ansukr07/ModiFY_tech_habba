# ZeroCIBIL — remaining features

**Inventory date:** 21 November 2026 (reconciled against the current worktree). **Scope:** synthetic demo only, per user direction; production lending and provider integration are not demo completion requirements. This is not a claim of production lending readiness.

## Current progress

The core synthetic journey exists: owner login, shop and application creation, simulated evidence selection and bank verification, lender queue and assessment, saved decisions, stress scenarios, lender approve/decline/reduce/request-evidence actions, owner evidence responses, reports, audit views, portfolio counts, and a fixture-based fairness comparison. The API has role and ownership checks. The Python service loads trained joblib scores, but the credit verdict still uses `heuristic-v0` policy thresholds. The dataset, rails, and bank statements are synthetic or simulated; the trained scores are uncalibrated for Indian MSME lending.

This inventory is based on the current routes and implementation in `apps/web/src/App.jsx`, `apps/api/src/createApp.js`, `ml/service.py`, and the gap notes in `features.md` and `docs/technical-architecture.md`. Older README text describing a fixed-only frontend is stale.

## P2 — production integration and controls

These are separate from the synthetic prototype and require lender, data-provider, and compliance decisions.

| Feature | Remaining behavior / acceptance |
| --- | --- |
| Real evidence connections | Replace fixture AA/UPI/GST and bank review with authorized provider flows, consent, identity binding, source references, revocation, and data-retention rules. Preserve the rule that PDFs are unverified supporting evidence. |
| Service authentication | Implemented in code: production scorer routes require `SCORER_API_KEY`; API and scorer enforce a 32-character minimum and the API forwards the key. Production config enforces HTTPS for remote scorer/browser origins and rejects scorer URL credentials. Remaining: provision secrets and verify TLS termination in deployment. |
| Durable writes | Partial: production requires explicitly configured MongoDB on a replica set or sharded cluster. Application creation, owner bank/evidence submissions, bank review (including release assessment), scoring (including failure status), and lender actions commit their related records, audit, status, and idempotency response in one transaction. Local memory and standalone Mongo remain nontransactional. Confirm transaction behavior and retry handling against the production topology before deployment. |
| Operational security | Partial: production now requires an explicitly configured durable MongoDB URI with TLS for remote databases, a 32+ character session secret, and the scorer key; it rejects in-memory storage and sets session cookies `Secure`. Async route failures now reach a common sanitized JSON error handler with request IDs; malformed and oversized bodies return explicit 400/413 errors. The API emits structured production access logs without query strings and applies per-IP in-process limits (60 login attempts, 300 reads, 120 other writes per minute; health checks exempt); limits execute before JSON body parsing. API tests cover login and read throttling. Production API startup rejects non-HTTPS browser origins and remote scorer URLs without HTTPS. Expired buckets are pruned and tracked clients are capped. Proxy IP trust is disabled locally and set to one hop in production, which requires exactly one trusted reverse proxy in front of the API. These controls are per-process and need a shared rate limiter, centralized log retention/alerting, monitoring, backup/restore, and financial-record retention/deletion procedures for deployment. Validate owner/lender/bank access on real tenancy data. |
| Credit lifecycle | If actual lending is in scope, add explicit human final approval, agreement/consent, disbursal, repayment servicing, and status reconciliation. None is implemented or promised by the current demo. |
| Real-world model validation | Collect consented Indian MSME outcomes, validate drift, calibration and subgroup performance, and set a governed retraining/review process before representing scores as real default or fraud probabilities. |

## Remaining work summary

**Synthetic demo completion:** live UI walkthroughs for remaining evidence variants and two-session report freshness; full keyboard and contrast review; complete the saved-decision compatibility path in the end-to-end walkthrough. In-app status refresh is the owner notification scope; email/SMS is not required for this demo.

**Model evidence limits:** the saved B-full metrics/report provenance needs reconciliation, and authenticity AUC/AP cannot be calculated without the absent original transaction CSV. These research gaps do not block the synthetic walkthrough; keep the current limitations visible and do not infer population, per-archetype, or hard-case performance from demo fixtures.

**Out of scope for this synthetic demo:** configure production secrets/TLS and Mongo transactions; add shared rate limiting, centralized log retention/alerts, monitoring, backup/restore, data retention/deletion, and real tenancy access validation. Real AA/UPI/GST provider connections, owner email/SMS, agreements, disbursal, servicing, and real-world model calibration require provider, lender, and compliance decisions.

## Explicit boundaries

No CIBIL-derived score, autonomous approval, live disbursal, production AA/GST login, or real-world default claim is part of the current prototype. LangGraph agent orchestration and lean-window-only stress adjustments appear in design notes but are optional refinements, not gaps that block the present deterministic underwriting journey. New endpoints are unnecessary for the P0 work unless verification exposes a missing contract.
